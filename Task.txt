PROJECT: NTU Cyber Security Society — Official Website

1. Your Mission

Act as an award-winning web designer, creative director, senior Next.js engineer, UI/UX specialist, and security-conscious full-stack architect.

Design and build the official website for the Cyber Security Society at National Textile University (NTU), Faisalabad, Pakistan.

The objective is to create a distinctive, premium, production-ready university society website that feels deliberately designed by an experienced professional team.

This must NOT look like a typical AI-generated landing page, a generic SaaS template, or a university assignment.

Build a complete, responsive, multi-page website with a functional, secure admin panel, real Supabase integration, image storage, and a deployment-ready Vercel configuration.

You have creative freedom to make high-quality design and technical decisions. Do not ask for approval for every minor implementation decision. Use sensible defaults, but never invent official university information, society achievements, member identities, or contact details.

2. Project Identity

- University: National Textile University (NTU), Faisalabad, Pakistan.
- Organization: Cyber Security Society.
- Design direction: Clean light, premium editorial, modern academic technology.
- Primary users: Students, faculty, prospective members, alumni, and cybersecurity professionals.
- Frontend: Next.js App Router, TypeScript, and Tailwind CSS.
- Backend services: Supabase.
- Image and media storage: Supabase Storage.

3. Art Direction: Clean Light, Premium, Professional

The website must use a light visual theme as its primary identity.

Think of a professionally art-directed university technology organization, a premium research publication, and a modern cybersecurity community.

Color palette

Start with a restrained palette:

- Primary background: warm white or a very subtle neutral.
- Secondary surfaces: soft gray or off-white.
- Primary text: deep charcoal or ink navy.
- Accent: sophisticated blue or restrained electric blue.
- Supporting colors: muted slate and accessible neutral borders.

Use color consistently through design tokens. Refine the palette to create a distinctive identity.

Do not make every section white. Establish visual rhythm through alternating backgrounds, full-width photography, editorial layouts, typography, and occasional dark contrast sections.

Typography

Choose a refined, highly readable type system.

Use:

- Strong editorial headings.
- Comfortable body text.
- Clear hierarchy between page titles, section titles, labels, and supporting copy.
- Restrained font weights.
- Appropriate line lengths and whitespace.

Use a professional font pairing or a carefully selected single type family. Load fonts efficiently and avoid layout shifts.

Layout

Create a deliberate grid with:

- Consistent page gutters.
- Generous but controlled whitespace.
- Clear alignment.
- Varied section compositions.
- Large, well-cropped photography.
- Carefully sized content containers.
- Balanced proportions between text and images.

Avoid making every section a centered heading followed by three identical cards.

Strict anti-AI design rules

Do not use:

- Purple gradients or neon backgrounds by default.
- Glassmorphism everywhere.
- Random decorative blobs.
- Excessive glowing effects.
- Repeated rounded cards for every content type.
- Generic stock illustrations of hooded hackers.
- Fake terminal animations.
- Matrix-rain backgrounds.
- Unnecessary floating elements.
- Oversized headings without meaningful content.
- Excessive scroll-triggered animation.
- Emoji as professional interface icons.
- Fabricated testimonials or fake counters.

The design must derive its character from composition, typography, photography, spacing, and content—not visual gimmicks.

Use subtle motion only where it enhances usability.

6. Secure Admin Panel

Build a real admin panel that allows authorized society administrators to maintain the website without editing source code.

Use a visually consistent but functional admin interface. Keep it simpler than the public-facing website.

Admin features

Implement content management for:

- Team members.
- Events.
- Projects and research.
- Educational resources.
- Gallery images.
- Homepage featured content.
- Membership applications, if enabled.

Provide:

- Create, edit, publish, unpublish, and delete operations.
- Image selection or upload to Supabase Storage.
- Form validation.
- Confirmation before destructive actions.
- Clear success and error feedback.
- Empty states and loading states.
- Search and filtering for large collections.

Use draft and published states where appropriate. Public pages must display only content intended for publication.

Authentication and authorization

Use Supabase Auth.

Requirements:

- Protected admin routes.
- Server-side authorization checks.
- A clear sign-in and sign-out experience.
- A secure initial-admin provisioning procedure.
- Role-based permissions if more than one administrative role is required.

Never rely solely on client-side route guards.

Do not expose service-role credentials in browser bundles.

Never allow anonymous visitors to modify published content, profiles, events, or administrator roles.

Membership applications and personal information must not be publicly readable.

Use Row Level Security (RLS) policies and test both authorized and unauthorized access.

Do not create a hardcoded password, fake authentication flow, or publicly accessible admin account.

7. Supabase Storage Architecture

Supabase Storage is the primary media storage solution.

Create a documented structure for:

- "branding"
- "team"
- "events"
- "projects"
- "gallery"

Use public read access only for approved assets intended to be publicly visible.

Use private buckets for sensitive or restricted files. Membership records and private administrative documents must not be placed in publicly readable buckets.

Implement:

- Upload and replacement workflows.
- Image preview before saving where practical.
- File type and size validation.
- Sensible filename handling.
- Storage path organization.
- Cleanup of replaced or deleted assets when safe.
- Appropriate access policies.
- Graceful handling of missing or unavailable images.

Store image paths or URLs in database records where appropriate.

Use Next.js image optimization and suitable responsive sizes. Configure remote image access only for trusted sources.

If no image has been uploaded, display a consistent, intentional fallback rather than a broken image.

8. Database Design

Create clean, typed, maintainable database schemas and SQL migrations.

Suggested tables:

- "profiles" or "team_members"
- "events"
- "projects"
- "resources"
- "membership_applications"
- "site_settings", if required

Use relationships, indexes, timestamps, and publication fields where appropriate.

Separate administrator permissions from ordinary profile information.

Implement appropriate RLS policies for each table and explain their intended access rules.

Validate input on the server. Use database constraints for important data integrity requirements.

Never include real credentials, private contact information, or invented production records in seed data.

Provide safe development seed data only when clearly labeled and easy to remove.

- Image crops.

- Long names and role titles.
- Portrait grids.
- Event details.

13. Implementation Workflow

Follow these phases autonomously.

Phase A — Inspect

Inspect the reference video, available files, and existing project structure. Identify the useful content patterns and the areas that should receive an original design.

Phase B — Plan

Establish the design system, routes, reusable components, database schema, storage architecture, authentication strategy, and deployment requirements.

Phase C — Build

Implement the complete public website and functional admin panel. Do not stop at the homepage or a static mockup.

Phase D — Integrate

Connect Supabase authentication, database operations, image storage, and public forms. Implement and verify access policies.

Phase E — Refine

Run the website, inspect the rendered pages, and refine typography, spacing, imagery, mobile layouts, and interactions. Remove generic or repetitive design patterns.

Phase F — Test

Check:

- Production build.
- TypeScript errors.
- Broken routes and links.
- Responsive layouts.
- Form submissions.
- Authentication.
- Unauthorized admin access.
- Database RLS policies.
- Storage permissions.
- Missing images.
- Browser console errors.
- Vercel deployment compatibility.

Fix issues rather than simply documenting them.

Phase G — Deliver

Provide complete source code, setup commands, environment documentation, SQL migrations, asset upload instructions, administrator setup, and deployment instructions.

Clearly identify any remaining configuration that requires real university information or credentials.

Never claim a feature works, a security policy is enforced, or a deployment succeeded unless it has actually been verified.
